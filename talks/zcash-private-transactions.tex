\begin{frame}{One payment, in indivisible units}
The \emph{ledger} is the accepted record of value transfers.
A \emph{transaction} proposes a change to that record.
One \emph{zatoshi} is $10^{-8}$ ZEC; amounts are integers.
\[
 \underbrace{80{,}000}_{\text{existing value}}
 =
 \underbrace{50{,}000}_{\text{payment}}
 +\underbrace{20{,}000}_{\text{change}}
 +\underbrace{10{,}000}_{\text{fee}}.
\]
\begin{itemize}
\item A \emph{note} privately describes an amount and receiving capability.
\item \emph{Change} is an output returned to the sender.
\item The \emph{fee} is publicly accounted value available to the
  producer who includes the transaction.
\end{itemize}
Create two new notes without publicly identifying the old note.
This is checked payment arithmetic, not a generated transaction.
\end{frame}

\begin{frame}{A private note needs a public representative}
A \emph{commitment} conceals a message while binding its creator
to that message, under the construction's security assumptions.
The message and randomness together are its \emph{opening}.
\[
 \cmsym=\NoteCommit(\text{receiver, value, creation data};\rcm).
\]
Here $\rcm$ is fresh commitment randomness. The ledger stores a
public value $\cmx$ derived from $\cmsym$, not the private note.

\medskip
A \emph{hash} maps data to a fixed-size summary, called a \emph{digest}.
Finding different inputs with the same digest is assumed infeasible
for the hashes used here.

\medskip
A hash is not automatically a hiding commitment: hashing a
small predictable amount would permit guessing it.
\end{frame}

\begin{frame}{Prove existence without revealing the position}
A \emph{hash tree} repeatedly hashes pairs of child values.
Its top value, the \emph{root}, commits to the leaves below it.
New note commitments are appended as leaves.

\medskip
A \emph{membership witness} contains the leaf position and the
sibling hashes needed to recompute the root. More generally, a
\emph{witness} is private data supporting a public claim.
\[
 \text{private old commitment}
 \longrightarrow \text{private path}
 \longrightarrow \text{public anchor}.
\]
An \emph{anchor} is an eligible earlier root.
A \emph{proof} lets a verifier check a claim about a witness;
the proof system used here is designed not to reveal that witness.

\medskip
Each \emph{shielded pool} maintains its own note tree, spent-tag set
and public aggregate balance.
\end{frame}

\begin{frame}{Prevent a second spend without removing a leaf}
Removing the old commitment would identify the spent note.
Instead, publish a \emph{nullifier}: its deterministic spend tag.
\[
 \nfsym=\mathsf{Nullifier}(\nksym,\text{old note}).
\]
The function uses a private nullifier key $\nksym$ and the note's
committed creation data.
\begin{itemize}
\item The same note and key give the same tag.
\item The proof connects the tag to the privately identified note.
\item The ledger rejects a repeated tag within that pool.
\end{itemize}
The tag is designed not to reveal which commitment was spent.
The tree keeps its old leaf; the ledger adds a spent tag.

\source{Functional interfaces here use the security assumptions;
the companion books specify the complete relations and exceptional cases.}
\end{frame}

\begin{frame}{Receiving, viewing and spending are different permissions}
A \emph{signature} is an approval of a message made with a secret
signing key and checked using its public verification key.
\begin{center}
\begin{tabular}{p{0.29\linewidth}p{0.60\linewidth}}
\toprule
Capability & What it permits\\
\midrule
Public receiver & Construct an output for the recipient.\\
Incoming viewing key & Discover and reconstruct matching incoming notes.\\
Full viewing key & Also compute known notes' nullifiers and derive
outgoing recovery keys.\\
Outgoing viewing key & Recover outputs whose sender actually enabled
recovery with that key.\\
Spending key & Approve spending; viewing alone does not grant this.\\
\bottomrule
\end{tabular}
\end{center}
A valid receiver does not prove that anyone possesses its spending key.
\end{frame}

\begin{frame}{Just enough algebra to explain delivery and balance}
The protocol uses a \emph{group}: a set of points with addition,
a zero point and subtraction, obeying the usual addition rules.
A \emph{scalar} is a number multiplying a point:
\[
 [a]P=\underbrace{P+\cdots+P}_{a\text{ additions}},\qquad
 [a+b]P=[a]P+[b]P.
\]
There are $r$ points, with $r$ a large prime: divisible only by $1$ and
itself. Scalar sums wrap around at $r$.
Recovering $a$ from $P$ and $[a]P$ is assumed hard for suitable points.

\medskip
A receiver contains a public \emph{diversifier} $d$, an address-variation
identifier, and a public transmission point $\pkd$:
\[
 \gd=\mathsf{DiversifyHash}(d),\qquad \pkd=[\ivk]\gd.
\]
DiversifyHash deterministically derives the public base point $\gd$.
The incoming viewing scalar $\ivk$ remains private.
\end{frame}

\begin{frame}{Deliver the note, then check what arrived}
For a fresh temporary scalar $\esk$, the sender publishes
$\epk=[\esk]\gd$ and obtains the shared point
\[
 S=[\esk]\pkd
   =[\esk][\ivk]\gd
   =[\ivk]\epk.
\]
The recipient computes the same point using $\ivk$.
A prescribed hash derives an encryption key from $S$ and $\epk$.

\begin{itemize}
\item Encryption turns note-reconstruction data and a \emph{memo},
  a sender-chosen message, into a \emph{ciphertext}, readable with that key.
\item An \emph{integrity tag} detects changes under the same key.
\item The recipient decrypts, checks the tag, reconstructs the note,
  and checks its derived temporary key and published commitment.
\end{itemize}
A valid payment proof does \emph{not} guarantee delivery:
a malicious sender can attach unrelated ciphertexts.
\end{frame}

\begin{frame}{Our payment uses two Actions}
An \emph{Action} pairs one old side with one new side.
A \emph{bundle} collects one pool's Actions and their shared data.
\begin{center}
\begin{tabular}{lrrr}
\toprule
Action & Old value & New value & Net value\\
\midrule
Real input to payment & $80{,}000$ & $50{,}000$ & $+30{,}000$\\
Dummy input to change & $0$ & $20{,}000$ & $-20{,}000$\\
\midrule
Total & $80{,}000$ & $70{,}000$ & $+10{,}000$\\
\bottomrule
\end{tabular}
\end{center}
A \emph{dummy input} has zero value and need not demonstrate old membership,
but still supplies a nullifier and a spend signature.
The public count does not identify which input is the dummy.

\medskip
Each new note's creation identifier is its paired old nullifier.
The pairing is protocol structure, not a public input-to-output link.
\end{frame}

\begin{frame}{Hide net values and randomise signing keys}
Let $V,R,G$ be prescribed public base points whose relative
multipliers are not known.
For Action $i$, choose fresh scalar randomness $\rcv_i$ and commit
to its private net value:
\[
 d_i=v_{{\rm old},i}-v_{{\rm new},i},\qquad
 \cvsym_i^{\rm net}=[d_i]V+[\rcv_i]R.
\]
Negative net values use group subtraction.

\medskip
Let $\asksym$ be the spend-authorising scalar and
$\aksym=[\asksym]G$ its public point.
Fresh scalar $\alpha_i$ randomises the signing key:
\[
 \rsk_i=\asksym+\alpha_i,\qquad
 \rksym_i=\aksym+[\alpha_i]G=[\rsk_i]G.
\]
The public $\rksym_i$ verifies this Action's spend signature.
Value commitments and signing keys serve different purposes.
\end{frame}

\begin{frame}{What the private relation must connect}
The public claim names the anchor, nullifier, new commitment,
net value commitment and randomised signing key.
The witness supplies old/new note data, the old path, viewing-key
components and the required randomness.

\begin{itemize}
\item The old commitment exists under the anchor when its value is nonzero.
\item The old receiver matches the viewing-key components, and the
  nullifier and randomised signing key follow from those same components.
\item The new commitment contains the intended new note data.
\item Both amounts satisfy $0\le v<2^{64}$.
\item Their difference opens the published net value commitment.
\item Nonzero old and new values are allowed by the selected pool rules.
\end{itemize}
The proof does not itself supply the spending-key signature,
check previous spends, or authenticate note delivery.
\end{frame}

\begin{frame}{1. Turn a computation into equations}
Arithmetic modulo $97$ identifies integers that differ by a multiple
of $97$. The resulting \emph{field} $\F_{97}$ supports addition,
multiplication and division by every nonzero value.

\medskip
An \emph{arithmetic circuit} is a fixed collection of cells connected
by equations. A private witness fills some cells; the public claim
fixes others. Consider
\[
 s^3+s+5=t\quad\text{in }\F_{97},\qquad s=3,\ t=35.
\]
Break the computation into rows:
\[
 s^2=9,\qquad s^3=27,\qquad s^3+s=30,\qquad 30+5=35.
\]
The same private $s$ must be used throughout: equality between
reused cells must also be enforced.

\medskip
This small-field example explains arithmetic, not cryptographic security.
\end{frame}

\begin{frame}{2. A complete four-row circuit}
Use columns $a,b,c$ for computed values.
Fixed coefficient columns $q$ select the equation on each row;
the public column $\pi$ supplies the claimed result.
\[
 q_Mab+q_La+q_Rb+q_Oc+q_C+\pi=0.
\]
\[
\begin{array}{c|rrr|rrrrr|r}
 i&a&b&c&q_M&q_L&q_R&q_O&q_C&\pi\\ \hline
 0&3&3&9&1&0&0&-1&0&0\\
 1&9&3&27&1&0&0&-1&0&0\\
 2&27&3&30&0&1&1&-1&0&0\\
 3&30&0&0&0&1&0&0&5&-35
\end{array}
\]
The required equalities are
\[
 a_0=b_0=b_1=b_2,\qquad c_0=a_1,\quad c_1=a_2,\quad c_2=a_3.
\]
Negative entries are residues modulo $97$.
\end{frame}

\begin{frame}{3. Columns become polynomials}
A \emph{polynomial} is a sum of coefficients times powers of $X$.
\emph{Interpolation} chooses its coefficients to match prescribed values.
Use row points $H=\{1,22,96,75\}\subset\F_{97}$:
\[
 \begin{aligned}
 a(X)&=90+61X+22X^2+24X^3,\\
 b(X)&=75+32X+25X^2+65X^3,\\
 c(X)&=65+16X+3X^2+22X^3.
 \end{aligned}
\]
Interpolate the fixed and public columns too.
Their equation becomes a polynomial $g(X)$.
The \emph{vanishing polynomial} $Z_H(X)=X^4-1$ is zero at every row point.
\[
 g(X)=(X^4-1)
 (61+70X+43X^2+47X^3+81X^4+46X^5).
\]
Every row satisfies the equation exactly when $Z_H$ divides $g$.
\end{frame}

\begin{frame}{4. Check the quotient at a new point}
The \emph{quotient} $q(X)$ is the second factor in $g(X)=Z_H(X)q(X)$.
At $x=20$, outside the row points,
\[
 Z_H(20)=46,\qquad q(20)=67,\qquad g(20)=75,
 \qquad 46\cdot67=75\pmod{97}.
\]
Change only $c_0$ from $9$ to $10$.
Polynomial division now leaves a nonzero \emph{remainder}:
\[
 r(X)=24(1+X+X^2+X^3).
\]
At $20$, the new numerator is $20$ while its quotient times $Z_H$ is
$64$: the identity test rejects.

\medskip
A nonzero polynomial has at most as many roots as its highest exponent.
Fixing the polynomials \emph{before} an unpredictable test point makes
a false identity hard to hide in a sufficiently large field.
\end{frame}

\begin{frame}{Halo authenticates the claimed evaluations}
A \emph{polynomial commitment} binds a hidden polynomial.
An \emph{opening proof} checks its claimed value at a chosen point
without sending all its coefficients.

\begin{enumerate}
\item Commit to the circuit columns with the prescribed privacy randomness.
\item Prove the equalities between reused cells and membership in
  required tables.
\item Combine the equations and commit to the quotient's pieces.
\item Derive later test points by hashing the preceding public record.
\item Check authenticated evaluations, ending in a checked group equation.
\end{enumerate}
That ordered record is the \emph{transcript}.
Its order prevents choosing earlier commitments after seeing later
challenges. A quotient identity with unauthenticated evaluations
would not be a proof.
\end{frame}

\begin{frame}{What the proof contract promises}
\begin{itemize}
\item \emph{Completeness}: honest valid inputs produce accepting proofs,
  subject to the construction's stated exceptional events.
\item \emph{Knowledge soundness}: a sufficiently successful prover can
  be converted, under the theorem's conditions, into an algorithm
  recovering a satisfying witness.
\item \emph{Zero knowledge}: the verifier's complete view can be
  simulated from public inputs alone.
\end{itemize}
These are complete proof-system claims under stated assumptions.
Commitment binding alone does not imply witness recovery.
Separately random-looking messages do not establish privacy of their
joint transcript.

\medskip
The private relation is one part of transaction validity,
not a substitute for the ledger's other checks.
\end{frame}

\begin{frame}{Conservation needs a binding signature}
For public pool withdrawal $b$, form the
\emph{binding verification key}
\[
 \mathsf{bvk}=\sum_i\cvsym_i^{\rm net}-[b]V.
\]
When the net private values sum to $b$, the value terms cancel:
\[
 \mathsf{bvk}=[\mathsf{bsk}]R,\qquad
 \mathsf{bsk}=\sum_i\rcv_i\pmod r.
\]
The \emph{binding signature} approves the transaction digest
using this aggregate randomness and base $R$.
For our payment,
\[
 30{,}000-20{,}000-10{,}000=0,\qquad
 \mathsf{bvk}=[\rcv_0+\rcv_1]R.
\]
Spend signatures approve use of individual spending authority.
The binding signature enforces aggregate conservation together with
the proof and signature assumptions. Amount and transaction-size bounds
exclude wraparound by a multiple of $r$.
\end{frame}

\begin{frame}{The signer must approve the user's payment}
The signature message is a prescribed digest of transaction data,
not a wallet's informal label for that data.
\begin{itemize}
\item The constructor selects the notes, recipients, change, fee
  and randomness.
\item The prover receives the private witness and therefore learns it.
\item The signer checks the intended recipient and amount,
  independently recognises change, and approves the exact effects.
\item The completed transaction is checked again before submission.
\end{itemize}
The approved effects include the ciphertexts: delivery data cannot
simply be replaced after signing.
A valid signature does not show that a user interface described
those effects honestly.

\end{frame}

\begin{frame}{The node checks the whole transaction}
A \emph{node} is a participating computer.
A validating node checks the applicable rules, not merely one proof.
\begin{enumerate}
\item Decode the transaction, enforce allowed operations and amount limits.
\item Verify its proof against the correct public inputs and the circuit's
  prescribed verification data.
\item Recompute the signature digest; verify spend and binding signatures.
\item Check eligible anchors and unused nullifiers, including duplicates
  inside this transaction and the containing block.
\item Validate any other transaction components and validity deadlines.
\item Check the public fee and resulting pool balances.
\end{enumerate}
For our all-shielded payment, the public withdrawal is the fee:
$b=f=10{,}000$.
Accepting it appends two commitments and inserts two nullifiers.
\end{frame}

\begin{frame}{A block gives the transaction its context}
A \emph{block} contains an ordered transaction list.
Its \emph{header} is a public summary naming the previous block
by hash and committing to the block's data.

\begin{itemize}
\item A \emph{branch} follows those parent links from the prescribed
  starting block. Its ledger state belongs to that branch.
\item A node validates the complete body and its header commitments,
  not an isolated list of transaction identifiers.
\item It checks the block's permitted new issuance, fees and allocations.
\item Transactions are checked against branch-local state, including
  changes from earlier transactions where the rules permit them.
\end{itemize}
A hash authenticates data; it does not validate the arithmetic
or authorisation inside that data.
\end{frame}

\begin{frame}{Confirmation is confidence in a branch}
\emph{Proof of work} is a publicly checkable result of computational
search. Zcash requires both its prescribed search solution and a
header hash no larger than the required difficulty target.

\medskip
\emph{Work} is the numerical score assigned from that target.
A node selects a visible, fully validated branch with the greatest
accumulated work, not merely the greatest number of blocks.

\begin{itemize}
\item Work does not excuse invalid transactions or a missing block body.
\item More work after a payment makes replacing its branch more demanding.
\item A competing valid branch can still remove a previously mined payment.
\end{itemize}
Confirmation confidence depends on assumptions about adversarial
computing power and network communication; it is not absolute finality.
\end{frame}

\begin{frame}{Discovery can use less than a full transaction}
A \emph{compact block} is a service's reduced representation
for wallet scanning, not a different block validated by nodes.
It carries nullifiers, new commitments, temporary public keys
and a prefix of each incoming ciphertext.

\begin{itemize}
\item Incoming viewing keys discover candidate receipts.
\item The wallet reconstructs each candidate note and checks its
  derived temporary key and commitment.
\item The compact prefix omits the memo and integrity tag.
  This is not full ciphertext authentication.
\item A full viewing key also computes known notes' nullifiers
  and matches them against observed spends.
\end{itemize}
Successful reconstruction identifies relevant data.
It does not prove that the server supplied a valid or complete chain.
\end{frame}

\begin{frame}{Discovery is not yet spendability}
To spend a discovered note, retain its content, pool, branch,
leaf position and path to an eligible anchor.

\begin{itemize}
\item Every Action appends a commitment, even if this wallet
  detects no receipt or the output has zero value.
\item After $n$ earlier commitments, the next $c$ outputs occupy
  positions $n,\ldots,n+c-1$.
\item Later appends change the sibling hashes needed by owned notes.
\item A small append summary suffices to compute future roots,
  but cannot recover arbitrary old membership paths.
\end{itemize}
Retain the additional tree data needed for owned notes,
and tie saved states to block identities.

\medskip
A root supplied by an untrusted server is not its own authentication.
\end{frame}

\begin{frame}{A reorganisation changes more than confirmations}
A \emph{reorganisation} switches the selected branch.
Suppose the shared ancestor has $11$ commitments.
Our outputs occupy positions $11,12$ on one branch.

\medskip
If a replacement branch adds three others before including the same
payment, its outputs instead occupy $14,15$.
\begin{itemize}
\item Roll back received-note locations, observed spends, tree state,
  retained paths and confirmations together.
\item Make corresponding database changes all visible together,
  or none of them.
\item Preserve the user's intention and retained transaction separately;
  recheck whether the payment is valid, conflicted or expired.
\end{itemize}
Re-labelling an old path with a new height does not make it valid.
\end{frame}

\begin{frame}{The privacy boundary includes the wallet service}
\begin{itemize}
\item A chain observer sees Action counts, pools, public balances,
  anchors, nullifiers, randomised public keys, commitments and ciphertexts.
\item A recipient learns its note and sender-chosen memo, not a
  cryptographic guarantee of the sender's real-world identity.
\item Viewing-key disclosure grants the corresponding viewing capability.
\item A wallet service can observe requests, connection metadata,
  relevant-transaction retrievals and broadcasts.
\item A server can omit relevant data; note reconstruction alone
  does not establish completeness or best-branch selection.
\end{itemize}
Zero knowledge protects the proof's private witness from its verifier.
It does not erase public inputs, network observations or information
deliberately shared with a prover.
\end{frame}

\begin{frame}{One payment, several distinct responsibilities}
\[
 \begin{gathered}
 \text{user-approved recipient, change and fee}\\
 \downarrow\\
 \text{notes, commitments, nullifiers and encrypted delivery}\\
 \downarrow\\
 \text{private proof, spend signatures and binding signature}\\
 \downarrow\\
 \text{transaction checks, block checks and branch selection}\\
 \downarrow\\
 \text{wallet discovery, retained paths and reversible state}.
 \end{gathered}
\]
No single accepting proof replaces the rest.

source pins and executable examples.}
\end{frame}
