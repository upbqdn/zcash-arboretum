\begin{abstract}
This volume of \emph{The Zcash Arboretum} constructs a private payment:
the sender's preparation, the recipient's recovery, and the public
checks that permit the payment to enter the accepted record. Orchard is
the payment construction; Ironwood names a separately accounted use of
that construction under the specified upgrade rules. It assumes the
\emph{Math Guide}'s field and curve constructions, the \emph{Crypto
Guide}'s commitments, signatures and encryption, the \emph{Halo 2 Guide}'s
proof contract, and the \emph{Consensus Guide}'s branch-local ledger
contract. Each derived object has an explicit type, purpose and consumer.
The distinction between a specified upgrade and an activated network rule
is maintained throughout. This exposition is non-normative.
\end{abstract}

\section{The shielded payment contract}\label{sec:intro}

The public ledger needs an authorised, value-preserving state transition.
A ledger, note, pool, anchor and nullifier have the interfaces introduced
in the \emph{Consensus Guide}, ``Ledger state and transaction acceptance''.
For the concrete primitives we use the \emph{Crypto Guide}, ``Groups,
commitments, and Sinsemilla'', ``RedPallas signatures'', and
``Key agreement and note encryption''. A proof's public inputs, private
witness and acceptance relation are constructed in the \emph{Halo 2
Guide}, ``From a relation to a circuit''.
A private payment must supply evidence of that transition without naming
the input note or publishing its value and recipient. Four mechanisms
divide the work: commitments represent hidden notes; nullifiers identify
repeated spends; proofs establish the private arithmetic relation; and
signatures authorise the transaction. Encryption delivers the new notes.
The node's branch-local state supplies the final existence and uniqueness
context.

This division matters. An accepting proof is not, by itself, a valid
transaction. It need not establish possession of a spending secret,
correct note delivery, absence of a previous nullifier, or the validity of
another pool's component. The full acceptance contract of the
\emph{Consensus Guide}, ``Ledger state and transaction acceptance'',
remains in force.

\subsection{Protocol, pool and rule set}\label{sec:intro-pools}

The \emph{Orchard protocol} is the shared cryptographic construction.
A \emph{pool} is a separate accounting and state namespace: its own note
tree, anchors, nullifier set and public value balance. The original
Orchard pool and the specified Ironwood pool use the same key and address
family. Sharing addresses does not merge their trees or spend histories.

An \emph{Action} is a record pairing one old note with one new note.
Either side can have value zero to fill an otherwise unused slot.
A \emph{bundle} collects one pool's ordered Actions and their shared
validation data. These are the units of construction throughout the book.
The \emph{lead byte} is the first byte of a delivered note's plaintext
and identifies its format. A transaction \emph{digest} is a hash of
prescribed transaction data. A \emph{cross-address restriction} requires
the old and new receivers within each Action to be equal.

Two rule profiles will be explicit:
\begin{itemize}[leftmargin=*]
\item The Orchard-pool construction uses note plaintext lead byte
  $\mathtt{0x02}$ and the version-5 transaction digest structure.
\item The specified NU6.3 profile adds Ironwood, lead byte
  $\mathtt{0x03}$, version-6 digests and the cross-address restriction
  used to seal the original Orchard pool.
\end{itemize}
The latter applies only where and when its defining consensus rules
activate. The guide does not infer a network's activation state from a
crate version or a ZIP status.

The principal source pin is \texttt{zips} commit \texttt{69610984};
the implementation references are \texttt{orchard}~0.15.0,
\texttt{librustzcash} commit \texttt{e30517e4}, and the
\texttt{orchard} development tree \texttt{bef8a27} where explicitly named.
The public \href{https://zips.z.cash/zip-0229}{ZIP~229},
\href{https://zips.z.cash/zip-0258}{ZIP~258} and
\href{https://zips.z.cash/zip-2005}{ZIP~2005} describe the specified
Ironwood changes. The version-6 details below use the published ZIP~229
revision consulted on 6 September 2026, including its explicit version
group and reserved-bit rules; those later clarifications are not
attributed to the older local ZIP commit. Their status is not an
activation certificate.

\subsection{Types and a continuing example}

The two primes and canonical encodings are constructed in the
\emph{Math Guide}, ``Pasta curves and their encodings''.
Let $p=p_{\Pallas}$ and $r=p_{\Vesta}$. Pallas points form a prime-order
group of order $r$, with coordinates in $\F_p$; the Action circuit is
over $\F_p$.
In particular $p<r$. Converting a canonical integer in $[0,p)$ into a
scalar in $\F_r$ is an injective conversion of integer representatives,
not a field homomorphism. For example, $(p-1)+1=0$ in $\F_p$, whereas
the same integer representatives sum to $p\ne0$ in $\F_r$.

The notation $\mathrm{LE}_k(x)$ denotes $k$ little-endian bits.
When a byte hash consumes such a string, pack each consecutive eight
bits into a byte, least significant bit first. We write
$\operatorname{enc}_{n}(x)$ for an unsigned integer's $n$-byte
little-endian encoding; for a field or scalar at width $32$, encode its
canonical representative. Signed encodings use the explicitly marked
two's-complement convention. Write $P^\star$ for a compressed $32$-byte
Pallas point encoding. The coordinate extractor is
$\Extract(P)=x(P)$ for an affine point and $\Extract(\mathcal O)=0$.
It is not a point encoding: $P$ and $-P$ have the same extraction.

The continuing example spends an $80{,}000$-zatoshi note, pays
$50{,}000$, creates $20{,}000$ change and pays a $10{,}000$ fee. It uses
two Actions: one pairs the real input with the payment; one pairs a
zero-valued dummy input with change. Their private net values are
$+30{,}000$ and $-20{,}000$. These are checked arithmetic examples, not
a claim that the text contains a generated production proof.

\section{Keys and viewing capabilities}\label{sec:keys}

An address lets another party create a payable note. A viewing key
discovers and interprets notes. A spending key authorises their
consumption. The construction must bind these capabilities together
without publishing the secret authorising scalar.

\subsection{Expansion and spend authority}\label{sec:keys-spend}

For a $32$-byte secret $s$ and byte string $t$, define
\[
 \mathsf{PRFexpand}_s(t)=
 \mathsf{BLAKE2b}_{512}(\texttt{Zcash\_ExpandSeed},s\|t).
\]
This uses personalised \emph{unkeyed} BLAKE2b with a secret prefix, not
BLAKE2b's native keyed mode. Its required pseudorandom-function property
is an assumption discussed in the \emph{Crypto Guide}, ``Hash functions
and key derivation''. Define $\mathrm{ToBase}$ and $\mathrm{ToScalar}$ by
reading the $64$-byte output little-endian and reducing modulo $p$ and
$r$, respectively. The reduction bias of a uniform $512$-bit input is
bounded by the target modulus divided by $2^{512}$; PRF-generated inputs
add the computational PRF distinction.

From spending key $\mathsf{sk}$ derive
\begin{align*}
 a&=\mathrm{ToScalar}(\mathsf{PRFexpand}_{\mathsf{sk}}(\mathtt{0x06})),\\
 \nksym&=\mathrm{ToBase}(\mathsf{PRFexpand}_{\mathsf{sk}}(\mathtt{0x07})),\\
 \rivk&=\mathrm{ToScalar}(\mathsf{PRFexpand}_{\mathsf{sk}}(\mathtt{0x08})).
\end{align*}
Let $G=\GroupHash^{\Pallas}(\texttt{z.cash:Orchard},\texttt{G})$,
using the group-hash construction in the \emph{Crypto Guide},
``Hash functions and key derivation''. Reject $a=0$. If $[a]G$ has odd
canonical $y$ coordinate, set $\ask=-a$; otherwise set $\ask=a$.
Then $\aksym=[\ask]G$ has even $y$ and is nonidentity.

The canonical sign permits $\Extract(\aksym)$ to identify $\aksym$ in
the next construction. It does not mean that every Pallas point can be
encoded by its $x$ coordinate without an additional convention.

\subsection{Viewing keys and addresses}\label{sec:keys-view}

The full viewing key is
$\fvk=(\aksym,\nksym,\rivk)$. Instantiate Sinsemilla's short commitment
under domain \texttt{z.cash:Orchard-CommitIvk}:
\begin{align*}
 \ivk&=\CommitIvk_{\rivk}
       \bigl(\Extract(\aksym),\nksym\bigr),\\
 &=\mathsf{ShortCommit}_{\texttt{z.cash:Orchard-CommitIvk},\rivk}
       \bigl(\mathrm{LE}_{255}(\Extract(\aksym))
                         \|\mathrm{LE}_{255}(\nksym)\bigr).
\end{align*}
The construction and its exceptional value $\bot$ are defined in the
\emph{Crypto Guide}, ``Groups, commitments, and Sinsemilla''.
Reject an output of zero or $\bot$ when deriving a receiving key.
A successful $\ivk\in[1,p)$ converts to a nonzero Pallas scalar by this
canonical-integer convention.

Let
\begin{align*}
 R&=\mathsf{PRFexpand}_{\operatorname{enc}_{32}(\rivk)}
       \bigl(\mathtt{0x82}\|\aksym^\star
                            \|\operatorname{enc}_{32}(\nksym)\bigr),\\
 \dk&=R[0:32],\qquad \ovk=R[32:64].
\end{align*}
The byte slicing uses a half-open interval. A single expansion output
supplies both keys. The incoming viewing key in the complete wallet
sense is $(\dk,\ivk)$: $\ivk$ performs decryption, while $\dk$ generates
the wallet's indexed diversifiers.

A diversifier $d$ is an $11$-byte string. Define
\[
 \gd=\mathsf{DiversifyHash}(d),\qquad \pkd=[\ivk]\gd,
 \qquad \mathsf{addr}=(d,\pkd).
\]
The diversification hash is
$\GroupHash^{\Pallas}(\texttt{z.cash:Orchard-gd},d)$, with its identity
output replaced by the fixed result for the empty message in the same
domain. Thus the protocol's diversified base is nonidentity.
The raw receiver is $d\|\pkd^\star$, $43$ bytes. Canonical point decoding
and nonidentity checks are necessary when accepting an address from
another party.

\subsection{Internal scope and capability limits}\label{sec:keys-scope}

A wallet can separate externally issued addresses from its internal
change addresses while retaining the same spend-authorising scalar.
Its internal full viewing key keeps $\aksym$ and $\nksym$ and replaces
the commitment randomness by
\[
 \rivk_{\rm int}=
 \mathrm{ToScalar}\!\left(
 \mathsf{PRFexpand}_{\operatorname{enc}_{32}(\rivk)}
  (\mathtt{0x83}\|\aksym^\star\|\operatorname{enc}_{32}(\nksym))
 \right).
\]
Apply the preceding incoming and outgoing derivations to that tuple.
Standard spending-key validity includes nonzero, nonexceptional incoming
keys for both external and internal scopes. This construction is ZIP~32's
Orchard internal key derivation, implemented in
\texttt{orchard/src/keys.rs}.

\begin{center}
\begin{tabular}{@{}p{0.22\linewidth}p{0.71\linewidth}@{}}
\toprule
Capability & What possession permits\\
\midrule
Receiver & Create payments; it is not an authorisation secret.\\
Incoming key & Discover and decrypt matching incoming notes; derive
addresses when the diversifier key is included.\\
Full viewing key & Additionally compute nullifiers of known notes and
derive the specified outgoing recovery keys; it does not sign spends.\\
Spending authority & Produce spend signatures; with note and state data,
construct complete spends.\\
\bottomrule
\end{tabular}
\end{center}

An outgoing viewing key recovers only outputs whose sender used that
key for outgoing recovery. A sender may deliberately omit that recovery
capability. A full viewing key therefore does not reveal every possible
outgoing payment of a malicious or independently configured spender.
Nor does possession of a public receiver prove that its advertised owner
knows the spending secret: the sender can validate encodings, but cannot
perform a recipient's private key-generation checks.

\section{Notes and their commitments}\label{sec:mint}

A note is the private description of value that a later proof will
consume. Its commitment must bind the amount and receiving capability
while concealing them from a chain observer.

\subsection{The committed note}\label{sec:mint-note}

Write a note as
\[
 \mathbf n=(d,\pkd,v,\rho,\psi,\rcm),
 \quad 0\leq v<2^{64},\quad \rho,\psi\in\F_p,\quad \rcm\in\F_r.
\]
The diversified base $\gd$ is reconstructed from $d$.
The amount's circuit range is $64$ bits; transaction and chain money
bounds are separate checks, not a reason to omit this range constraint.

Define its $1086$-bit message
\begin{align*}
 m(\mathbf n)={}&
 \gd^\star\|\pkd^\star\|\mathrm{LE}_{64}(v)\\
 &\|\mathrm{LE}_{255}(\rho)\|\mathrm{LE}_{255}(\psi),
\end{align*}
where compressed point bytes are interpreted as the corresponding
$256$ bits. The note commitment and its published extraction are
\[
 \cmsym=\NoteCommit_{\rcm}(m(\mathbf n)),\qquad
 \cmx=\Extract(\cmsym).
\]
The commitment is SinsemillaCommit under
\texttt{z.cash:Orchard-NoteCommit}. The lower primitive pads the final
partial ten-bit chunk according to its fixed-length convention; an
application must not insert a byte-alignment pad between $\rho$ and
$\psi$. The point commitment is used in the nullifier equation, while
only $\cmx$ is appended to the note tree.

For genuinely uniform independent $\rcm$, the randomisation component
has the hiding property proved for the commitment primitive. In honest
notes $\rcm$ is derived from a seed and other note data. Their hiding
argument is computational and depends on the expansion function's
security; it is not a claim of unconditional hiding of the whole
transaction.

\section{Nullifiers and authenticated existence}\label{sec:spend}

A commitment does not disappear when spent. Removing the input leaf
would reveal the spend-to-note link. The ledger instead keeps all
commitments and records a separate public tag on consumption.

\subsection{The nullifier equation}\label{sec:spend-nullifier}

Let
\[
 K=\GroupHash^{\Pallas}(\texttt{z.cash:Orchard},\texttt{K}),\qquad
 F_{\nksym}(\rho)=\mathsf{Poseidon}(\nksym,\rho).
\]
The Poseidon instantiation is the fixed-length-two
$\mathsf{P128Pow5T3}$ construction over $\F_p$, with three state words
and two input field elements, constructed in the \emph{Crypto Guide},
``Hash functions and key
derivation''. For note $\mathbf n$ with point commitment $\cmsym$,
\begin{equation}
 \nfsym=\Extract\left([a]K+\cmsym\right),\qquad
 a=\operatorname{repr}_{[0,p)}
            \bigl(F_{\nksym}(\rho)+\psi\bigr).
 \label{eq:iw-nullifier}
\end{equation}
The sum is first reduced in $\F_p$; its canonical integer $a$ then
converts to $\F_r$ for scalar multiplication. Adding instead in $\F_r$
would be a different function.

For fixed note and key components this equation is deterministic.
With commitment and key-binding security, a valid spend cannot choose
a new tag for the same nonzero note. The public node rejects any repeated
tag in the relevant pool, including repeats in the same transaction or
block. Determinism alone does not prove that arbitrary maliciously
chosen notes have collision-resistant nullifiers; the complete argument
also uses the commitment construction and how note uniqueness is
established.

Every new note uses $\rho_{\rm new}=\nfsym_{\rm old}$ from its own Action.
Since accepted nullifiers are unique within a pool, accepted output
notes have distinct creation identifiers there. This includes zero-value
outputs. Across two pools there are separate nullifier namespaces; no
global uniqueness claim follows merely from this rule.

\subsection{Reconstructing a note from a seed}\label{sec:mint-rseed}

The sender draws a fresh $32$-byte $\mathsf{rseed}$. Its first required
input is $\rho$: the nullifier of the old side of the same Action,
just constructed in \S\ref{sec:spend-nullifier}. A dummy old side still
produces a nullifier, so this rule applies even when no real note is
consumed.

Derive
\begin{align*}
 \mathsf{esk}
 &=\mathrm{ToScalar}\bigl(
   \mathsf{PRFexpand}_{\mathsf{rseed}}
     (\mathtt{0x04}\|\operatorname{enc}_{32}(\rho))\bigr),\\
 \psi
 &=\mathrm{ToBase}\bigl(
   \mathsf{PRFexpand}_{\mathsf{rseed}}
     (\mathtt{0x09}\|\operatorname{enc}_{32}(\rho))\bigr).
\end{align*}
Redraw the seed if the ephemeral scalar $\mathsf{esk}$ is zero.
For an Orchard lead-byte-$\mathtt{0x02}$ note,
\[
 \rcm=\mathrm{ToScalar}\bigl(
   \mathsf{PRFexpand}_{\mathsf{rseed}}
      (\mathtt{0x05}\|\operatorname{enc}_{32}(\rho))\bigr).
\]
For a specified Ironwood lead-byte-$\mathtt{0x03}$ note, instead compute
\begin{align*}
 t_{\rcm}={}&\mathtt{0x0b}\|\gd^\star\|\pkd^\star
       \|\operatorname{enc}_{8}(v)\\
       &\|\operatorname{enc}_{32}(\rho)
        \|\operatorname{enc}_{32}(\psi),\\
 \rcm={}&\mathrm{ToScalar}
             (\mathsf{PRFexpand}_{\mathsf{rseed}}(t_{\rcm})).
\end{align*}
The preimage after the seed has $137$ bytes:
$1+32+32+8+32+32$. Its fields are byte encodings, unlike the
$255$-bit field encodings inside $m(\mathbf n)$.
The dependency order is forced: derive $\psi$ before the version-3
$\rcm$. Both versions use the same $\mathsf{esk}$ and $\psi$ formulas.

The version-3 change binds the seed derivation to the other note fields
as specified in ZIP~2005. It does not make the payment proof,
signatures or key agreement independent of discrete logarithms.
No alternate recovery protocol is needed to understand these bytes.

If note commitment evaluation fails with $\bot$, honest construction
retries with fresh randomness. The formal Action relation's treatment
of exceptional Sinsemilla cases is different and is stated explicitly
in \S\ref{sec:action-stmt}.

\subsection{The note tree}\label{sec:tree}

The note tree has depth $32$ and leaf capacity $2^{32}$. Leaves are
published $\cmx$ values in transaction and Action order. Unfilled leaves
contain the fixed sentinel $2\in\F_p$.

It is convenient to count hash height from the leaves. For
$j=0,\ldots,31$, first compute
\[
 h_j(l,r)=
 \mathsf{ShortHash}_{\texttt{z.cash:Orchard-MerkleCRH}}
  \bigl(\mathrm{LE}_{10}(j)\|
        \mathrm{LE}_{255}(l)\|\mathrm{LE}_{255}(r)\bigr).
\]
Then set $H_j(l,r)=0$ if $h_j(l,r)=\bot$, and
$H_j(l,r)=h_j(l,r)$ otherwise. This conversion is the concrete
\textsf{MerkleCRH} rule, also implemented in
\texttt{orchard/src/tree.rs}; an exceptional hash is not a separate
non-field object stored in the public tree.
Each preimage has $520$ bits, exactly $52$ ten-bit chunks.
The first combine above leaves uses $j=0$; the root combine uses
$j=31$. The Sinsemilla short-hash construction, including its exceptional
semantics, is in the \emph{Crypto Guide}, ``Groups, commitments, and
Sinsemilla''. The required exceptional-case hardness prevents an efficient
adversary from deliberately obtaining such a zero hash.

For a leaf position $i\in[0,2^{32})$, let $i_j$ be bit $j$ of $i$ and
$s_j$ the sibling at height $j$. Starting with $r_0=\cmx$, compute
\begin{equation}
 r_{j+1}=
 \begin{cases}
 H_j(r_j,s_j),&i_j=0,\\
 H_j(s_j,r_j),&i_j=1.
 \end{cases}
 \label{eq:iw-path}
\end{equation}
The path has $32$ siblings, or $1024$ bytes of field encodings,
and a position determining left versus right. The final value $r_{32}$
is the root.

The proof keeps the position and siblings private. Its public anchor
identifies a candidate tree, not the spent leaf. This does not make every
leaf an equally plausible input: publicly identifiable dummy outputs,
already explained spends and external metadata can reduce anonymity.

\subsection{Anchors and zero-value inputs}\label{sec:tree-anchor}

All Actions in one bundle use its common public anchor. The node checks
that it is eligible in that pool on the candidate branch. Under the
modern rule this is an earlier block's final treestate, not a tree
invented by the prover and not an intermediate state of the same block.

In the ordinary nonexceptional path calculation, the circuit gates
membership by old value:
\[
 v_{\rm old}(r_{32}-\mathsf{anchor})=0.
\]
For a nonzero $64$-bit old amount, the factor is nonzero in $\F_p$, so
the root must equal the anchor. A zero-valued old side may have no
membership witness to an accepted note. This permits dummy spends and
shielding. It does not permit a positive-value invented input.
The Action still has other constraints, a nullifier and a spend
signature; dummy does not mean an arbitrary unvalidated byte record.

The formal circuit contract has two additional allowances, stated in the
protocol specification's ``Merkle Path Validity'' and ``Action Statement''
notes. Intermediate hash inputs can use $255$-bit representatives that
reduce to the assigned field values without being their canonical
representatives. The membership check may also pass if a hash on the path,
including the root, is zero. Write $\mathsf{PathOK}$ for this permitted
predicate, rather than silently identifying it with an ordinary canonical
path recomputation. The zero-hash allowance models incomplete Sinsemilla
addition. Its security argument needs the exceptional-case hardness
assumption; honest public tree computation still uses the canonical
function $H_j$ above.

\subsection{Action value and authorisation keys}\label{sec:iw-action-keys}

Before encrypting an output, construct two public Action fields that the
delivery and proof algorithms will consume. The first hides its net value.
Using the commitment construction in the \emph{Crypto Guide}, ``Groups,
commitments, and Sinsemilla'', define
\[
 V=\GroupHash^{\Pallas}(\texttt{z.cash:Orchard-cv},\texttt{v}),\qquad
 R=\GroupHash^{\Pallas}(\texttt{z.cash:Orchard-cv},\texttt{r}).
\]
Their required independence means no efficiently known discrete-log
relation, not linear independence in a cyclic group.
For Action $i$, let $d_i=v_{{\rm old},i}-v_{{\rm new},i}$, sample
$\rcv_i\in\F_r$, and publish the net value commitment
\[
 \cvsym_i^{\rm net}=[d_i]V+[\rcv_i]R.
\]
A negative integer coefficient denotes the negative of the corresponding
positive multiple. The values remain integers even though multiplication
uses their residues in $\F_r$.

The second field is a randomised spend-authorisation key. Sample
$\alpha\in\F_r$ and set
\[
 \rsk=\ask+\alpha,\qquad
 \rk=\aksym+[\alpha]G=[\rsk]G.
\]
Resample if $\rsk=0$, equivalently if $\rk=\mathcal O$, since consensus
prohibits that public key. The circuit will connect $\rk$ to the old
note's receiving authority; a later signature will demonstrate approval
under $\rsk$. The zero-valued dummy old side uses a fresh valid spending
key of the constructor's choice and follows the same construction.

\section{Note delivery and recovery}\label{sec:delivery}

The proof can establish that an output commitment contains a well-formed
note without giving its recipient the information needed to spend it.
Delivery is a separate protocol. A malicious sender can create an
undeliverable output; ordinary transaction validation does not promise
otherwise.

\subsection{Encrypting the note}\label{sec:delivery-sender}

For lead byte $\ell$, the note plaintext is the fixed $564$-byte string
\[
 \mathsf{np}=\ell\|d\|\operatorname{enc}_{8}(v)
       \|\mathsf{rseed}\|\mathsf{memo},
\]
where the memo occupies exactly $512$ bytes. The first $52$ bytes contain
all note reconstruction data except $\rho$, which is taken from the
Action nullifier. The format supplies the recipient's diversified base
through $d$; the recipient recovers $\pkd$ from its viewing key.

Using the nonzero ephemeral scalar already derived, compute
\begin{align*}
 \mathsf{epk}&=[\mathsf{esk}]\gd,&
 S&=[\mathsf{esk}]\pkd,\\
 k_{\rm enc}
 &=\mathsf{BLAKE2b}_{256}
   (\texttt{Zcash\_OrchardKDF},S^\star\|\mathsf{epk}^\star).
\end{align*}
Encrypt $\mathsf{np}$ with ChaCha20-Poly1305, nonce $0^{96}$ and empty
associated data. The result $C_{\rm enc}$ has $580$ bytes, including the
$16$-byte authentication tag. The \emph{Crypto Guide}, ``Key agreement and
note encryption'', constructs the cipher and its security contract.

The fixed nonce is safe only under the construction's key-freshness
conditions. Reusing seed and context can reuse a key; the nonce is not
a substitute for fresh output randomness. Honest key generation and
seed sampling are therefore part of the encryption security assumptions.

The recipient computes the same shared point because
\[
 [\ivk]\mathsf{epk}=[\ivk][\mathsf{esk}]\gd
                  =[\mathsf{esk}]\pkd.
\]
This is a group identity. Confidentiality of the resulting ciphertext is
a computational claim under key-agreement, key-derivation and cipher
assumptions, not a consequence of the identity alone.

\subsection{Outgoing recovery}\label{sec:delivery-out}

For Action net value commitment $\cvsym^{\rm net}$, derive
\[
 k_{\rm out}=\mathsf{BLAKE2b}_{256}
 \bigl(\texttt{Zcash\_Orchardock},
    \ovk\|(\cvsym^{\rm net})^\star
        \|\operatorname{enc}_{32}(\cmx)\|\mathsf{epk}^\star\bigr).
\]
The commitment was constructed in \S\ref{sec:iw-action-keys}.
Encrypt $\pkd^\star\|\operatorname{enc}_{32}(\mathsf{esk})$ using the
same authenticated-encryption-with-associated-data (AEAD) convention.
The $64$-byte plaintext yields an $80$-byte
$C_{\rm out}$. An auditor with $\ovk$ can recover $\pkd$ and
$\mathsf{esk}$, derive the incoming key material and recover the note.

The sender can instead choose a fresh random outgoing key and random
outgoing plaintext, withholding outgoing recovery. The ciphertext is
not proof that a particular $\ovk$ was used. Nor does a decryptable
memo authenticate a real-world sender identity.

\subsection{Recipient acceptance}\label{sec:delivery-recv}

For each candidate Action and each incoming key, perform the following:
\begin{enumerate}[leftmargin=*]
\item Decode the ephemeral point canonically and apply the required
  nonidentity check. Compute $[\ivk]\mathsf{epk}$ and the incoming KDF.
\item Open the full incoming ciphertext with AEAD verification. Reject
  failure and a lead byte not allowed for this pool and format.
\item Parse $d$, $v$ and $\mathsf{rseed}$, and take
  $\rho=\nfsym$ from the same Action. Compute $\gd$ and
  $\pkd=[\ivk]\gd$.
\item Recompute $\mathsf{esk}$, $\psi$ and the correct version's $\rcm$.
  Check $[\mathsf{esk}]\gd=\mathsf{epk}$.
\item Recompute the note commitment and require its extraction to equal
  the published $\cmx$. Only then record a detected note.
\end{enumerate}
The ephemeral-key check binds the recovered seed to the transmitted
ephemeral key. The commitment check binds the recovered note fields to
the published output. A successful AEAD opening alone is insufficient.

Compact scanning omits the memo and authentication tag and therefore
uses the stream-cipher prefix plus these reconstruction checks, not a
successful full AEAD verification. It discovers candidate notes against
supplied chain data; it does not itself validate that chain.

Shielded coinbase has special public recovery rules. Its prescribed
outgoing viewing key is zero, allowing validators and any observer to
recover the output plaintext and check its required format and values.
The ordinary incoming privacy discussion must not be applied to coinbase
outputs without this exception.

\section{Actions and the proof relation}\label{sec:action}

An \emph{Action} pairs one old side with one new side. The pairing fixes
the new note's creation identifier. It does not disclose to a chain
observer which old note is used, or whether either side has zero value.

\subsection{Public encoding and private witness}\label{sec:action-stmt}

The Action wire record is
\[
 (\cvsym^{\rm net},\nfsym,\rk,\cmx,
                      \mathsf{epk},C_{\rm enc},C_{\rm out}).
\]
The first five fields are each $32$ bytes; the ciphertexts are $580$
and $80$ bytes. Thus one Action record is $820$ bytes.
Its spend-authorisation signature is a separate $64$-byte field.
The bundle adds shared flags, signed value balance, anchor, aggregate
proof and a \emph{binding signature}, the signature enforcing its combined
value balance.

For the specified cross-address circuit, the public instance vector is
\[
 \bigl(\mathsf{anchor},x(\cvsym^{\rm net}),y(\cvsym^{\rm net}),
       \nfsym,x(\rk),y(\rk),\cmx,e_s,e_o,\delta\bigr).
\]
The point-coordinate representation assigns the identity the pair $(0,0)$
where it is permitted; other points use their affine coordinates.
External parsing must match it. Consensus separately prohibits identity
$\rk$, while the value commitment can be identity.
There are ten field elements. The flags $e_s,e_o$ enable nonzero spends
and outputs. The flag $\delta$ disables transfers between different
receivers. Consensus and the selected verification key determine which
flag values apply; they are not free choices of the witness.

The witness contains the old side's $\gd,\pkd,v,\rho,\psi,\rcm$ and point
commitment, the new side's $\gd,\pkd,v,\psi,\rcm$, the old note's membership
path and position, $\aksym,\nksym,\rivk$, a spend-key randomiser $\alpha$,
and value-commitment randomness $\rcv$. It does \emph{not} contain
$d$, $\mathsf{rseed}$, $\mathsf{esk}$, the ciphertexts or $\ask$.
This is why proving can be separated from authorising a spend.
The proof does not check the honest seed-expansion or diversification-hash
procedures; recipient reconstruction checks the delivered note against
them. The original circuit's nine-element instance omits $\delta$ and
the additional cross-address condition.

\begin{definition}[Action relation]\label{def:action}
The typed witness and public inputs satisfy:
\begin{enumerate}[leftmargin=*,label=\textbf{A\arabic*.}]
\item The old point commitment equals the note commitment computed from
  its witnessed fields, or that computation returns $\bot$.
\item With $\rho_{\rm new}=\nfsym$, the new commitment's extraction equals
  public $\cmx$, or that computation returns $\bot$.
\item Either $v_{\rm old}=0$ or the old membership witness satisfies
  $\mathsf{PathOK}$ for the public anchor, including its explicitly
  permitted representation and exceptional-case semantics.
\item Both amounts are in $[0,2^{64})$ and
  $\cvsym^{\rm net}=[v_{\rm old}-v_{\rm new}]V+[\rcv]R$.
\item The old fields and nullifier key give public $\nfsym$ by
  \eqref{eq:iw-nullifier}.
\item The randomised spend key satisfies $\rk=\aksym+[\alpha]G$.
\item The old receiving key satisfies
  $\pkd_{\rm old}=[\ivk]\gd_{\rm old}$ with
  $\ivk=\CommitIvk_{\rivk}(\Extract(\aksym),\nksym)$,
  or that short-commitment evaluation returns $\bot$.
\item The spend gate satisfies $v_{\rm old}(1-e_s)=0$.
\item The output gate satisfies $v_{\rm new}(1-e_o)=0$.
\item If $\delta=1$, both
  $\gd_{\rm old}=\gd_{\rm new}$ and
  $\pkd_{\rm old}=\pkd_{\rm new}$ hold as full points.
\end{enumerate}
Witness typing requires $\aksym$, both diversified bases and both
diversified transmission keys to be nonidentity Pallas points.
Unlike honest key generation, the Action witness permits either sign of
$\aksym$. Its incoming-key commitment uses only $\Extract(\aksym)$;
knowledge of the authorising secret up to sign is sufficient. Scalar
representatives used only in an isolated multiplication may be
noncanonical when reduction gives an equivalent witness. The nullifier
scalar and incoming scalar, whose values also participate elsewhere, need
the prescribed canonical decompositions. Field, value-range and boolean
constraints are part of the relation.
\end{definition}

The Sinsemilla $\bot$ alternatives are real weakenings of the simple
mathematical equalities, not successful honest note construction.
Excluding adversarial exploitation requires the primitive's exceptional
case hardness argument under its generator assumptions. A proof of the
weakened relation alone does not justify dropping these alternatives
from a security reduction.

The last condition consists of four field equations:
\[
 \delta(x(P_{\rm old})-x(P_{\rm new}))=0,\qquad
 \delta(y(P_{\rm old})-y(P_{\rm new}))=0
\]
for $P=\gd,\pkd$. Equality of extracted coordinates alone would permit
opposite points and would not express equality of receivers.

\subsection{How the circuit implements the relation}\label{sec:circuit}

The \emph{Halo 2 Guide}, ``From a relation to a circuit'', constructs the
constraint language and its connection to a proof.
A \emph{gadget} is a reusable group of circuit constraints implementing
one operation. A \emph{limb} is a bounded positional digit, such as a
ten-bit digit in base $2^{10}$.
Here the private integer $v$ is represented by bounded limbs. Range lookups and
reconstruction equations ensure that the field value is the intended
$64$-bit integer. A signed difference can be represented by a bounded
magnitude and sign in $\{-1,+1\}$, so fixed-base multiplication commits
to the integer difference with its proper sign.

The note-commitment gadget decomposes its assigned points and field values
into the constrained bit sequence corresponding to \S\ref{sec:mint-note},
subject to the specification's representation allowances and including the
$255$-bit boundaries.
In \emph{fixed-base multiplication} the point is fixed by the circuit;
in \emph{variable-base multiplication} it is supplied as part of the
instance or witness. Elliptic-curve constraints implement the fixed-base
multiplications for commitments and randomised keys, and variable-base
multiplication for the old transmission key. The Poseidon gadget
implements $F_{\nksym}(\rho)$; the tree gadget implements the $32$
hashes of \eqref{eq:iw-path}. Copy constraints tie repeated values to
the same assigned witness, rather than allowing independently chosen
copies.

A field equation only proves its advertised integer statement after the
relevant range and canonicality conditions have been established.
Similarly, a scalar-multiplication gadget must constrain its base to the
intended point. These are obligations of the actual circuit, not facts
supplied by the notation $[a]P$.

The source implementation is \texttt{orchard}~0.15.0,
\texttt{src/circuit.rs}, with note and incoming-key gadgets in
\texttt{src/circuit/note\_commit.rs} and
\texttt{src/circuit/commit\_ivk.rs}. The instance offsets put
$\delta$ at index $9$. Circuit versions choose different verification
keys. A verifier must select by the applicable consensus rules, not let
the prover select a weaker historical key.

The aggregate proof covers all Actions of a bundle with their ordered
instances. It does not verify the blockchain's preceding proofs.
The fixed construction uses $2^{11}$ circuit rows per Action; aggregating
$m$ Actions gives the specified proof byte length $2720+2272m$.
For two Actions this is $7264$ bytes. These implementation parameters
describe the pinned proof format, not a universal lower bound on
zero-knowledge proof sizes.

\section{Balance, digests, and authorisation}\label{sec:spend-value}

The Action relation relates each hidden old value to its paired new
value. The transaction needs a single public net balance and explicit
approval of the transaction data. Two signature roles complete those
obligations.

\subsection{Value commitments and integer conservation}

Using the already constructed $\cvsym_i^{\rm net}$, $d_i$, $V$ and $R$,
for the bundle's signed public balance $b$ compute
\[
 \mathsf{bvk}=\sum_i\cvsym_i^{\rm net}-[b]V.
\]
If $b=\sum_i d_i$ as integers, the value terms cancel and
\[
 \mathsf{bvk}=[\mathsf{bsk}]R,\qquad
 \mathsf{bsk}=\sum_i\rcv_i\pmod r.
\]
The binding signature uses the RedPallas binding base $R$ and the
transaction signature digest. Honest correctness is the displayed group
identity plus signature correctness.

Conversely, an unbalanced set of extracted commitment openings leaves
\[
 \mathsf{bvk}=[D]V+[\textstyle\sum_i\rcv_i]R,\qquad
 D=\sum_i d_i-b.
\]
A sound balance argument must connect a valid binding signature to
knowledge or unforgeability under this related public key, and then to
the inability to know a nontrivial relation between $V$ and $R$.
It is not valid to infer knowledge of $\mathsf{bsk}$ merely from
commitment binding. The required signature and proof composition
assumptions are recorded in \S\ref{sec:security}.

Finally, a group equation yields equality modulo $r$. The transaction's
bounds lift it to integer equality. With fewer than $2^{16}$ Actions,
$64$-bit input and output ranges, and $|b|\leq2.1\cdot10^{15}$,
\[
 |D|\leq m(2^{64}-1)+|b|<2^{81}<r.
\]
Thus $D=0\bmod r$ implies $D=0$ as an integer. The Action count bound is
also far looser than what the block-size limit permits.
Omitting this step would leave a modular conservation claim rather than
a monetary one.

\subsection{Spend authorisation}\label{sec:spend-auth}

The randomised key $(\rsk,\rk)$ was constructed in
\S\ref{sec:iw-action-keys}. The circuit proves its public-key equation.
The spender then signs the
transaction digest under $\rsk$ using RedPallas SpendAuth.
The exact nonce generation, challenge hash, encoding checks and
verification equation are constructed in the \emph{Crypto Guide},
``RedPallas signatures''. With nonce point $R_s$ and challenge $c$,
the verification identity has the form
$[s]G=R_s+[c]\rk$.

Fresh randomisation makes $\rk$ appear unrelated to $\aksym$ under the
stated key distribution, but does not hide every other transaction field.
The authorising signature says that the party controlling the
corresponding secret approved the signed digest. The proof connects
that key to the old note's receiving capability.
Neither fact alone is the complete spending-authority argument.

A dummy spend also has a randomised key and a signature. Its key can be
freshly generated by the transaction constructor; the membership gate
permits its zero old value. Its nullifier must nevertheless be unused.

\subsection{The complete version-5 byte envelope}\label{sec:iw-wire}

Serialization and hashing are different algorithms: their field order
need not be the same. Here is the complete serialization for the
Orchard-only payment, using the CompactSize construction from the
\emph{Consensus Guide}, ``Blocks and branch-local validation''.

First emit the five four-byte little-endian header fields:
\[
 \mathtt{0x80000005},\quad \mathtt{0x26A7270A},\quad
 \beta,\quad 0,\quad \eta.
\]
The high version bit is set as required; $\beta$ is the target
height's consensus branch identifier. Lock time is zero in this example;
$\eta$ is the chosen valid expiry height, or zero where disabling expiry
is permitted. These fields occupy $20$ bytes.

Next emit four single zero bytes: transparent input count, transparent
output count, Sapling spend count and Sapling output count. Their arrays
are empty, and no conditional Sapling balance, anchor or binding
signature is present. Version~5 has no Sprout component.
For the nonempty Orchard bundle, emit in order:
\begin{enumerate}[leftmargin=*]
\item CompactSize Action count $m$, followed by the $m$ Action records
  of \S\ref{sec:action-stmt}, each $820$ bytes.
\item One flags byte, $e_s+2e_o$, with its remaining bits zero under
  the version-5 encoding rules.
\item Signed eight-byte value balance $b$, then the $32$-byte anchor.
\item CompactSize proof length $2720+2272m$, then exactly that many
  proof bytes.
\item The $m$ spend signatures, each $64$ bytes, in Action order.
\item The $64$-byte binding signature.
\end{enumerate}
When $m=0$, only its zero count is present; all those additional
Orchard fields are absent. In a general transaction the transparent and
Sapling counts instead govern their complete compatibility components.
Their specialized parser must consume and validate those components
before returning control at the Orchard count.

For $m=2$, the proof length $7264$ has a three-byte CompactSize encoding.
The full ordinary Orchard-only transaction therefore has
\[
 20+4+1+1640+1+8+32+3+7264+128+64=9165
\]
bytes. This is the actual format's size calculation, not a fabricated
proof or transaction test vector.

\subsection{Version-5 effecting and authorising digests}
\label{sec:spend-sighash}

Write $H_t(m)=\mathsf{BLAKE2b}_{256}(t,m)$ for a fixed $16$-byte
personalisation $t$. For all Orchard Actions in order, form
\begin{align*}
 D_c&=H_{\texttt{ZTxIdOrcActCHash}}
  \left(\mathop{\|}_i
   (\operatorname{enc}_{32}(\nfsym_i)\|
    \operatorname{enc}_{32}(\cmx_i)\|
    \mathsf{epk}_i^\star\|C_{{\rm enc},i}[0:52])\right),\\
 D_m&=H_{\texttt{ZTxIdOrcActMHash}}
       \left(\mathop{\|}_i C_{{\rm enc},i}[52:564]\right),\\
 D_n&=H_{\texttt{ZTxIdOrcActNHash}}
  \left(\mathop{\|}_i
   ((\cvsym_i^{\rm net})^\star\|\rk_i^\star\|
     C_{{\rm enc},i}[564:580]\|C_{{\rm out},i})\right).
\end{align*}
The component digest for a present Orchard bundle is
\[
 D_O=H_{\texttt{ZTxIdOrchardHash}}
    (D_c\|D_m\|D_n\|\mathsf{flags}\|
           \operatorname{enc}_{8}^{\rm signed}(b)\|
           \operatorname{enc}_{32}(\mathsf{anchor})).
\]
An absent component instead hashes the empty string under its component
personalisation. The hashes of an empty component and a nonempty
zero-value component are not interchangeable.

The transaction identifier is
\[
 \mathsf{txid}
 =H_{\texttt{ZcashTxHash\_}\|\operatorname{enc}_{4}(\beta)}
          (D_h\|D_t\|D_S\|D_O).
\]
Here $\beta$ is the consensus branch identifier.
The header digest $D_h$ hashes, under \texttt{ZTxIdHeadersHash}, the
five four-byte fields in order: version header, version-group identifier,
branch identifier, lock time and expiry height.
The transparent and Sapling component digests are $D_t$ and $D_S$.
For the all-shielded example with neither component present they are
the empty hashes under \texttt{ZTxIdTranspaHash} and
\texttt{ZTxIdSaplingHash}. When those components are present, their
complete ZIP~244 rules must be used; this is a compatibility interface,
not a permission to commit only their totals.

For a transaction with no transparent inputs, the shielded signature
digest equals this transaction identifier. With transparent inputs it
uses ZIP~244's transparent signature digest, committing additionally to
their spent output amounts and scripts and using the required
$\mathsf{SIGHASH\_ALL}$ mode for shielded authorisations. In particular,
the signer needs authenticated previous-output data; an untrusted
coordinator's claimed input total is not enough.

The Orchard authorising-data component is
\[
 A_O=H_{\texttt{ZTxAuthOrchaHash}}
       (\mathsf{proofs}\|\mathop{\|}_i\mathsf{spendSig}_i
                                \|\mathsf{bindingSig}).
\]
The root authorising digest uses personalisation
$\texttt{ZTxAuthHash\_}\|\operatorname{enc}_{4}(\beta)$ and the
transparent, Sapling and Orchard authorising digests in order.
This digest is committed by the block's authorising-data tree, constructed
in the \emph{Consensus Guide}, ``Authenticated block history''.

Excluding signatures and proofs from $\mathsf{txid}$ avoids a signing
cycle: signatures sign effecting data and subsequently enter a separate
digest. Ciphertexts remain in effecting data. The proof need not check
their content for the authorising signatures to bind their exact bytes.

\subsection{The specified version-6 extension}\label{sec:pools-v6}

Version~6 adds an Ironwood component after Orchard. Its root effecting
and authorising digests have a fifth and fourth component child,
respectively. For the affected shielded components the anchor moves from
effecting to authorising data. Thus a changed anchor can require a new
proof and authorising-data commitment without changing $\mathsf{txid}$
or, for the no-transparent-input case, the signed digest.

Its wire header changes to $\mathtt{0x80000006}$ and version group
$\mathtt{0xD884B698}$; the latter is also the constant
\texttt{V6\_VERSION\_GROUP\_ID} at the pinned library source.
After the complete Orchard component, serialize the Ironwood component
using the same count, Action, flags, balance, anchor, proof-length,
proof and signature ordering as above. Its count is always present;
the additional fields are present only when that count is nonzero.
Moving anchors between digest categories does \emph{not} move their
positions in this wire encoding. The flag interpretation is
pool-specific and is fixed in \S\ref{sec:turnstile}.

The concrete changed personalisations in ZIP~229 are:
\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
Digest & Version-6 personalisation\\
\midrule
Orchard component & \texttt{ZTxIdOrchardH\_v6}\\
Orchard authorising component & \texttt{ZTxAuthOrchaH\_v6}\\
Ironwood component & \texttt{ZTxIdIronwd\_H\_v6}\\
Ironwood compact Actions & \texttt{ZTxIdIrnActCH\_v6}\\
Ironwood memos & \texttt{ZTxIdIrnActMH\_v6}\\
Ironwood noncompact Actions & \texttt{ZTxIdIrnActNH\_v6}\\
Ironwood authorising component & \texttt{ZTxAuthIrnwdH\_v6}\\
\bottomrule
\end{tabular}
\end{center}
The Orchard Action-part personalisations remain their version-5 values.
For each present version-6 bundle, append its anchor after the existing
authorising-component fields and omit it from the effecting-component
preimage. An absent bundle hashes empty input under its own domains.
Sapling's changed noncompact-spend and authorising domains are
\texttt{ZTxIdSSpendNH\_v6} and \texttt{ZTxAuthSapliH\_v6}.
Other version-5 components retain their defined structure.

Anchor movement does not detach a proof from its anchor: the anchor
remains a proof instance, and the full authorising data remains committed
by the block. It changes which commitment identifies that proof-bearing
transaction representation.

\section{Pool rules and complete validation}\label{sec:pools}

A bundle is one pool's ordered Actions, shared flags, anchor, value
balance, aggregate proof and signatures. The same transaction can contain
both pool components. Each has its own anchor and binding key, while all
authorisations bind the complete transaction digest.

\subsection{The conditional seal}\label{sec:turnstile}

Under the specified NU6.3 rules, an Orchard-pool coinbase component must
be empty, each Orchard Action disables cross-address transfer, and each
transaction has $b_{\rm Orchard}\geq0$. These rules apply to the pool
regardless of whether the transaction uses version~5 or version~6.
They permit value to leave the pool and permit retained value to return
to the same receiver; they prohibit net entry and ordinary transfers
between different receivers within that pool.

For Ironwood, bit $2$ is the specified
$\mathsf{enableCrossAddress}$ flag, and the circuit input is
$\delta=1-\mathsf{enableCrossAddress}$. Bits $0$ and $1$ are spend and
output enable flags. Reserved bits must be zero. The Orchard component's
bit $2$ remains reserved as zero in the specified transaction rules;
the node supplies the required cross-address restriction for that pool
and branch. A parser accepting a bit pattern does not establish that the
whole consensus verifier accepts it.

For a $70{,}000$-zatoshi migration and a $10{,}000$ fee,
\[
 b_{\rm Orchard}=80{,}000,\qquad b_{\rm Ironwood}=-70{,}000.
\]
The public fee remains $10{,}000$. Pool balances change in opposite
directions, but neither pool's tree acquires the other pool's leaves.
Keys and receiver encodings need not change merely because the pool
namespace changes.

\subsection{The node's checklist}\label{sec:action-verify}

For an ordinary transaction, a validating node:
\begin{enumerate}[leftmargin=*]
\item Selects the network rules at the candidate block height and checks
  transaction version, version-group and branch identifiers, canonical
  lengths and all resource bounds.
\item Parses all field elements, points, signatures and proof encodings
  with their specified canonicality and identity conditions. Checks
  flags and the required nonempty input/output structure.
\item Builds each pool's ordered public instances, including its anchor
  and the branch-required cross-address semantics. Verifies the
  aggregate proof under the selected verification key.
\item Recomputes the correct version's transaction signature digest.
  Verifies every spend signature and each bundle's binding signature
  under its recomputed binding key.
\item Checks each anchor against eligible earlier final treestates in
  the correct pool and branch. Rejects repeated nullifiers within the
  transaction, earlier transactions in the block, or the parent state.
\item Validates every other component under its own rules. Checks
  transparent input availability and maturity, lock time, expiry,
  money ranges, fee, pool restrictions and resulting chain balances.
\item Proposes pool-local nullifier insertions and commitment appends in
  their defined order. Checks capacity and commits them only with the
  successfully validated whole block.
\end{enumerate}
Coinbase replaces the ordinary spend and fee conditions with its special
issuance and recovery rules. A node still verifies its applicable proofs,
bindings and public accounting.

The ledger uses explicit lookup for nullifier freshness. In principle a
different protocol could prove nonmembership relative to a committed
state. It is inaccurate to say that global-history checks can never be
represented in a proof; that is simply not how this acceptance contract
is divided.

\section{One payment, end to end}\label{sec:action-walk}

Alice has a detected, unspent $80{,}000$-zatoshi note and its path to an
eligible anchor. Bob supplies a validated receiver. Alice also derives
an internal receiver for change. Choose a pool and branch profile that
permit both resulting recipients; the sealed original Orchard pool
would not permit this ordinary cross-address transfer after its seal.

\begin{enumerate}[leftmargin=*]
\item Reconstruct the old note commitment and nullifier from its recorded
  seed, creation identifier and keys. Confirm locally that its path
  gives the intended anchor.
\item Construct a fresh zero-valued dummy old note, with its own valid
  key material and nullifier. The two nullifiers must differ and neither
  may already be spent in the pool.
\item Pair the real old side with Bob's $50{,}000$ output and the dummy
  side with Alice's $20{,}000$ output. Each output takes its own paired
  old nullifier as $\rho$.
\item Sample fresh output seeds and derive note randomness in the
  correct version's order. Construct the two commitments. Choose fresh
  $\rcv_0,\rcv_1$ and $\alpha_0,\alpha_1$, retrying forbidden identity
  randomised keys.
\item Form the net commitments
  \[
   \cvsym_0=[30{,}000]V+[\rcv_0]R,\qquad
   \cvsym_1=[-20{,}000]V+[\rcv_1]R.
  \]
  Set the bundle public balance to $10{,}000$.
\item Encrypt both notes and optional outgoing recovery records.
  Assemble the Action effecting fields, shared flags and anchor.
  Generate the aggregate proof from the ordered witnesses and instances.
\item Recompute the complete transaction signature digest. Sign both
  Action keys and the binding key
  \[
   \mathsf{bvk}=\cvsym_0+\cvsym_1-[10{,}000]V
              =[\rcv_0+\rcv_1]R.
  \]
\item Serialize and run the complete local verification checks before
  submission. Retain the transaction identity and private output
  metadata needed for recovery.
\end{enumerate}

The public Action count is two; it does not label the dummy spend.
The public balance reveals the fee for this all-shielded transaction.
Bob detects his note through incoming decryption, not from an explicit
recipient field. Alice detects change under internal scope and later
recognises consumption of her original note through its nullifier.
Once mined, both commitments occupy definite positions in the selected
branch's pool tree. A later spend proves membership without disclosing
those positions.

\section{Security boundaries}\label{sec:security}

The construction supports a precise conditional argument, not a blanket
claim that a transaction reveals nothing except validity.

\subsection{What is mathematical}

The following conclusions are identities or elementary implications:
honest key agreement gives the same shared point; the randomised secret
and public key match; correctly balanced value commitments cancel to the
binding key; a nonzero bounded old value activates membership; bounded
modular equality lifts to integer balance; and identical accepted
nullifiers are rejected by the ledger's uniqueness rule.

These facts do not establish that a malicious prover cannot violate the
premises. The step from an accepting proof to a witness uses knowledge
soundness, and the step from a signature to authorised spending uses a
signature security argument with the relevant related-key structure.

\subsection{What is assumed or imported}

The application uses the commitment binding and exceptional-case
assumptions of the \emph{Crypto Guide}, ``Groups, commitments, and
Sinsemilla''; the expansion and nullifier-PRF assumptions of ``Hash functions
and key derivation''; the signature contract of ``RedPallas signatures'';
and the proof contract of the \emph{Halo 2 Guide}, ``Knowledge soundness
and zero knowledge''. For extracted malicious witnesses, a balance proof
must compose those contracts with the binding-signature argument and
the ledger's integer bounds.

Nullifier unlinkability additionally depends on the distribution of
honestly generated note data and the appropriate PRF- or group-based
argument. The protocol design gives alternative assumption routes; it
does not make unlinkability unconditional when viewing keys, note data
or addresses are disclosed.

Zero knowledge concerns the full joint proof transcript, with its
public instances fixed. It does not hide the public instances,
signatures, ciphertext lengths, pool balances or network behaviour.
Marginally random-looking columns or commitments are not a substitute
for the simulator and composition hypotheses of the proof system.
This volume imports that proof-system contract rather than claiming a
new complete simulator for deployed Halo 2.

\subsection{What remains visible or unavailable}

A chain observer sees transaction shape, pool membership, public
balances, anchors, nullifiers, randomised keys, output commitments and
ciphertexts. Public transfers, timings, repeated external addresses and
application disclosures may correlate them. Coinbase plaintexts have
the explicit public-recovery exception. A recipient learns its received
note and sender-chosen memo, not an authenticated real-world sender
identity supplied by the payment protocol.

A malicious sender can withhold delivery or outgoing recovery while
creating a consensus-valid output. A malicious wallet server can omit
data or present an incomplete branch view unless the client has an
independent authentication and availability strategy. A reorganisation
can remove a valid payment from the selected branch. None of these
events contradicts proof zero knowledge or commitment binding.
