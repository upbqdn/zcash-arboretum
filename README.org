#+TITLE: The Zcash Arboretum
#+AUTHOR: m@rek.onl
#+OPTIONS: toc:nil num:nil

The Zcash Arboretum explains the mathematics, cryptography and state changes
needed to understand a modern shielded Zcash payment. It builds the required
concepts before using them and carries one payment through the protocol,
wallet construction and recovery.

The material is *non-normative*. The [[https://zips.z.cash/protocol/protocol.pdf][protocol specification]],
applicable [[https://zips.z.cash/][ZIPs]] and network consensus rules remain authoritative.
A specified upgrade, an implementation release and network activation are
different facts. Each volume identifies its source baseline and distinguishes
proved statements, computational assumptions and unresolved design boundaries.

* Reading order

Read each volume after the prerequisites it names. Elementary arithmetic and
the ability to follow an algorithm are the starting point; specialist terms
are not assumed without an earlier explanation.

** Foundations

1. *Math Guide* (=math-guide.tex=): integers and encodings, prime fields,
   groups, probability, linear algebra, polynomials, fast transforms, Pasta
   curves, and the byte-field extension needed by AES.
2. *Crypto Guide* (=crypto-guide.tex=): security definitions, exact hash and
   key-derivation constructions, commitments, signatures, encryption,
   authenticated trees and wallet address encodings.
3. *Halo 2 Guide* (=halo2-guide.tex=): circuit constraints, permutation and
   lookup arguments, the masked inner-product commitment proof, multiple
   openings and the complete verifier transcript. A checked small-field
   computation connects the equations; it is not a production proof.

** Core protocol

4. *Consensus Guide* (=consensus-guide.tex=): branch-local ledger validation,
   blocks, work and difficulty, public accounting, authenticated block history
   and the conditional meaning of confirmation.
5. *Ironwood Guide* (=ironwood-guide.tex=): the Orchard payment construction
   and specified Ironwood rule profile—keys, notes, nullifiers, delivery,
   Action constraints, balance, versioned transaction bytes and authorisation.
6. *Wallet Guide* (=wallet-guide.tex=): seed and account derivation, addresses,
   receiver selection, fees and change, transaction construction, signer
   checks and recovery.
7. *Sync Guide* (=sync-guide.tex=): compact note discovery, commitment
   positions, retained paths, atomic scanning, rollback and server trust.

The shared payment spends an 80,000-zatoshi note, pays 50,000, returns 20,000
in change and leaves a 10,000 fee. Each core volume explains its own part of
that same transaction.

** Independent frontier endpoints

These are optional destinations, not prerequisites for the core payment.

8. *FlyClient Guide* (=flyclient-guide.tex=): authenticated work sampling,
   its conditional error bounds and the missing bridge to a complete Zcash
   light-client verifier.
9. *ZSA Guide* (=zsa-guide.tex=): asset identity, public issuance, private
   per-asset conservation, split inputs and the selected draft's unresolved
   transaction-format interfaces.
10. *Crosslink Guide* (=crosslink-guide.tex=): a pinned two-chain state
    machine, persistent finalised and bounded-available views, conditional
    safety proofs and the separate progress and implementation obligations.
11. *FROST Guide* (=frost-guide.tex=): shares, key generation, two-round
    signing, single-use nonce state and randomised threshold RedPallas
    integrated with transaction approval.

* Scope and editorial rule

Include a construction only when a retained endpoint needs it. Explain it
fully enough for that consumer; do not substitute its name for its definition.
A later glossary or forward reference does not repair an unexplained first use.
Shared notation and the binding writing rules live in
[[file:CONVENTIONS.org][CONVENTIONS.org]].

Earlier shielded and transparent components appear only at compatibility
interfaces required by the retained protocol. Their complete internals,
unneeded research surveys and historical implementation catalogues are outside
this project. Frontier mechanisms are not presented as activated network rules
or as proofs of an implementation merely sharing their name.

* Building and checking

Compile one volume with [[https://tectonic-typesetting.github.io/][Tectonic]]:

#+begin_src sh
tectonic -Z shell-escape <volume>.tex
#+end_src

Run the shared tooling, numerical examples and complete PDF gate:

#+begin_src sh
python3 -B site/tools/test_sitegen.py
python3 -B research/check_foundations.py
python3 -B research/check_mathcrypto.py
python3 -B research/check_halo2.py
python3 -B research/check_wallet_crypto.py
python3 -B research/check_deployed.py
python3 -B research/check_frontier.py
python3 -B site/tools/check_build.py
#+end_src

The PDF gate builds all eleven volumes, the presentation and the generated
complete edition. It retains logs and PDFs in =build/pdf/= and rejects
compilation errors, overfull boxes, unresolved references, duplicate labels
or destinations, and missing glyphs. Add =--update-pdfs= to copy the PDFs
beside their sources only after the entire gate passes.

The site workflow renders per-section HTML and builds the search index.
=site/tools/check_site.py= checks generated local links, anchors and error
markup. With the generated site served locally, the browser regression checks
search-result reachability and scrolling at phone, tablet and desktop sizes:

#+begin_src sh
uv run --with playwright python -B site/tools/check_search.py http://127.0.0.1:8768
#+end_src

An optional second argument selects =firefox= or =webkit= when their Playwright
binaries and runtime libraries are available. Viewport emulation is not a claim
to have tested every physical device.

Builds and example checks detect concrete errors; they do not prove every
statement or establish cryptographic hardness. Substantive prose also requires
independent mathematical, source and prerequisite-order review.
The current edition's review evidence and limitations are recorded in
[[file:research/verification.md][research/verification.md]].
